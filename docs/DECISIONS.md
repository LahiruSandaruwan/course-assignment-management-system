# Architecture and Design Decisions

- **Laravel Version**: Laravel 13 was specified in the assignment but requires PHP 8.3+; this environment provides PHP 8.2.12, so Laravel 12 was used instead. Architecture and idioms remain consistent with modern Laravel (bootstrap/app.php-based config, etc.).
- **Assignment Status**: A `status` field (`draft` / `published`) was added to the `assignments` table. Although not explicitly required by the assignment spec, it is necessary to control student visibility cleanly at the database and policy level. Students can only see published assignments.
- **Graded Submission Resubmission**: Resubmission is blocked once `status` is `graded` (student must contact instructor / no endpoint to override). This maintains grade integrity and prevents students from overwriting submissions after they have been evaluated.
- **Grading Concurrency (Pessimistic Locking)**: When grading submissions, we use `DB::transaction()` alongside `$submission->lockForUpdate()->firstOrFail()`. This guarantees that if two instructors (or an admin and an instructor) attempt to grade the same submission at the exact same millisecond, the second request will wait for the first to complete before reading the row. Simulating true concurrent HTTP requests with race conditions in PHP Pest feature tests is impractical because standard PHP testing operates synchronously in a single process. However, the use of `lockForUpdate` within a transaction is the industry standard for preventing lost updates in relational databases and correctly implements the required concurrency protection.
- **N+1 Performance Fix (Phase 8)**: 
  - **Problem**: When fetching the courses list, accessing related collections (e.g. `$course->students->count()`) forces the ORM to execute individual `SELECT` queries per course per relationship (the N+1 query problem).
  - **Measurement**: Using `DB::enableQueryLog()`, we measured that fetching 5 courses and echoing their instructor name, student count, and assignment count via lazy loading (`Course::all()`) took **16 queries** (1 for courses, 5 for instructors, 5 for students, 5 for assignments).
  - **Fix**: We updated `CourseService` to use eager loading for relationships and native database aggregations for counts: `Course::with('instructor:id,name')->withCount(['students', 'assignments'])`. 
  - **Result**: The measured query count plummeted from **16 queries to 2 queries** total (1 for the courses and their subquery counts, 1 `WHERE IN` for the instructors), regardless of whether there are 5 courses or 15.
  - **Scaling to 100,000 Courses**: At 100,000 courses, even 2 queries can overwhelm memory if retrieving everything at once (`Course::all()`). The approach must change to use `$query->paginate()` (which we already implemented), `select()` only the absolutely necessary columns, or cursor pagination (`cursorPaginate()`) for sequential API exports.
